## Why the domain model matters

If a system treats a feature, task, run, and session as basically the same thing, recovery and reporting turn into a mess.

Senderos should keep these concepts separate.

## Feature

A **feature** is the user-facing unit of intent.

Examples:

- Add passwordless login.
- Build CSV invoice export.
- Create docs app for the monorepo.

A feature typically owns:

- title and description,
- source reference,
- current lifecycle state,
- approved spec,
- acceptance criteria,
- dependencies,
- priority and labels.

## Task

A **task** is a concrete sub-unit of work under a feature.

Examples:

- draft spec,
- generate Gherkin,
- create implementation workspace,
- build frontend,
- run tests,
- open PR,
- clean temp directory.

Tasks may be generated by Senderos itself.

## Run

A **run** is one execution attempt of a workflow.

A feature can have several runs over time:

- initial kickoff,
- retry after failure,
- review-only run,
- repair run.

This matters because a failed run does not automatically mean the feature is dead.

## Session

A **session** is the external execution handle owned by an agent system.

Examples:

- a Codex session id,
- a Claude Code run id,
- an OpenClaw session key,
- a local subprocess handle.

Sessions are the bridge to resumability, status polling, and postmortem inspection.

## Workspace

A **workspace** is the repo location where implementation work happens.

Fields usually include:

- base repo path,
- temp directory,
- branch name,
- cleanup state,
- retained-for-debugging reason.

## Suggested feature lifecycle

```text
draft
→ clarifying
→ specified
→ approved
→ gherkinized
→ ready
→ queued
→ in_progress
→ blocked
→ review
→ merged
→ completed
→ canceled | failed
```

The important part is not dogma. The important part is having a lifecycle that is explicit enough to automate against.
